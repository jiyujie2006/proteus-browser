# M0 — Foundations & the Ruler: Current Status

This file distinguishes two facts that must not be conflated:

1. The **local ruler and tooling scaffold are runnable**.
2. The roadmap's **M0 milestone is not yet complete**, because no real Chromium
   patch series has been applied and no signed, reproducible Win/macOS/Linux
   engine build has been produced.

The hard milestone definition remains
[`docs/06-roadmap.md`](docs/06-roadmap.md). Local checks do not weaken it.

## Commands

```bash
# Install the exact test-only schema-validation dependencies.
npm ci

# Expected to pass: local ruler/tooling scaffold checks.
npm run m0:local

# Expected to remain non-zero until build-farm evidence exists.
npm run m0:milestone
```

Both commands print the same local and hard-exit audit. `m0:local` exits on
local regressions only; `m0:milestone` also requires real patch hunks, a
dedicated three-platform build workflow, independently authenticated
provenance, complete-bundle reproducibility evidence, and builder-attested live
reports.

## What still blocks the roadmap M0 exit

- All 17 Chromium patch files are metadata-only placeholders with no
  `diff --git` hunks. Production patch application fails closed.
- There is no dedicated Win/macOS/Linux Chromium build workflow.
- There are no signed complete engine bundles or independently authenticated
  reproducibility matches.
- There are no builder-attested live-harness reports proving that the observed
  runtime came from those exact bundles.
- There is no builder-attested disposable runner or platform containment
  boundary. Local process-group/`taskkill` cleanup is deliberately reported as
  best-effort, not as hostile-process containment.
- Effective generated GN args, complete pinned toolchains, platform
  signing/notarization, and build-derived SBOMs are not yet bound.
- The repository does not yet contain a governed, pinned M0 release public key;
  the assembler's real release path therefore cannot be used until that key is
  provisioned through the release process.

The implemented entrypoint layer binds two distinct paths and physical
identities, exact entrypoint/provenance/report bytes, the pinned Chromium source
and patch-series digests, declared invocation/platform fields, the controlled
probe bytes, and a V1–V5 runtime baseline whose summary is independently
recomputed. The baseline need not be green; that is M1/M2 work.

That layer intentionally reports
`entrypoint-release-signed-scaffold/v1`. The hard roadmap gate requires
`full-bundle-builder-attested/v1`, which additionally needs complete bundle
manifests, independently authenticated per-builder/workflow attestations,
effective args/toolchains, and an attested harness run. This prevents synthetic
test fixtures or a single release signer from turning the milestone green.

Chromium compilation also needs a real checkout, `depot_tools`, platform
toolchains, substantial disk/compute, codesigning/notarization, and build-farm
credentials. None of those are fabricated by the local gate.

## Parallel progress beyond M0

The non-UI **M1A config-generation core** is implemented under
[`fingerprint/`](fingerprint/): deterministic persona sampling, strict semantic
validation, a versioned shared seed dataset, a deterministic canonical JSON
contract for the strict Profile Config domain, Ed25519 signing, fail-closed
ingest verification, and Rust↔Node conformance vectors.

That work reduces M1 risk but does not satisfy the native-engine exit criteria.
M1 still requires real Chromium config ingest, native surfaces, cross-context
propagation, and external/runtime verification.
